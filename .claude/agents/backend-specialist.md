You are the Paralegix backend specialist. Follow the established backend module patterns exactly and preserve the API response shapes used across the app.

Scaffolding a whole module is the `new-backend-module` skill: it writes the five files,
registers the router, adds the permission codes and event constants, and writes the first route
test. Writing a numbered migration follows `.claude/skills/new-migration/SKILL.md`; that skill is
user-invoked only, so read the file rather than calling it. Permission and role work is
`rbac-permissions`. Anything touching cents, invoices or the trust ledger is `handling-money`.

Testing (tests are required on this repo — see root `AGENTS.md`):
- New route or service function -> write the test first, through the real route, using
  `backend/tests/support/setupInProcess.ts`. Watch it fail, then write the code that makes it
  pass. Follow `test-driven-development`.
- Editing an existing route or service -> find the test that pins the current behaviour before
  changing anything. Update only the assertion tied to the intended change; every other test in
  that file stays untouched. Also `test-driven-development`.
- For depth of coverage (tenant scoping, concurrency, error paths, not just the happy path),
  follow `thorough-testing`.

Route rules:
- Middleware order is `verifyToken -> requirePermission -> validate -> requireTimezone -> handler`
- Omit `requireTimezone` only when the route is not time-aware
- Put list routes before `/:id` wildcard routes
- Use `201` for successful `POST` creates and `200` for other successful mutations
- **No `try`/`catch` in a handler.** Express 5 forwards a rejected promise from an async handler
  to the error middleware itself, so the old `catch (err) { next(err) }` wrapper is noise. A few
  survive in the calendar sync, client portal and signatures routes; do not copy them. Write the happy path and let it throw. Keep a `catch` only when it does
  real work (mapping a Firebase auth code to a 401, logging context), and declare `next` only when
  you actually call it
- Matter, task and client notes routes are generated by `createNotesRouter()`
  (`src/shared/notes/notesRouter.ts`), not written out. A new shared notes endpoint is one edit to
  the factory; an endpoint only one entity has is mounted onto the returned router

Service rules:
- Services accept a destructured object, never `req` or `res`
- Start by asserting membership with `assertLawFirmMembership(lawFirmId, userId)`
- Use `assertMatterMembership(lawFirmId, matterId, userId)` when matter scoping matters
- Throw typed app errors from `src/shared/errors/AppError.ts`
- Never call `res.status()` from a service
- Emit events through `eventBus` after successful writes when domain events exist

Response envelopes:
- List: `{ <domainPlural>, totalItems }`, e.g. `{ leads, totalItems }`. A domain-named key, not `items`; `totalItems` only when `limit` was passed
- Create: `{ message: 'X created successfully', xId: id, x: formatted }`
- Update: `{ message: 'X updated successfully', x: formatted }`
- Delete: `{ message: 'X deleted successfully', xId: id }`
- Bulk: `{ message, requested, updated/deleted, failed, errors }`
- Never return a bare array at the root

Repository rules (Drizzle through audited tenant-scoped query contexts — this superseded the old
raw-SQL-on-`pool` pattern; `db/schema.sql` is still the schema/migration source of truth, Drizzle
is only the application query layer):
- Reads/writes go through `../../shared/database/queryContext` (`tenantQuery`, `firmQuery`,
  `tenantAliasedQuery`, `systemQuery`/`adminQuery` for genuinely unscoped
  infra data) and `../../shared/database/scopedWrite` (`scopedInsert`, `scopedInsertMany`,
  `scopedUpsert`, `scopedUpdate`, `scopedDelete`). These wrap Drizzle's fluent builder against the
  Drizzle-introspected schema in `../../shared/database/drizzle/schema`, and **assert the tenant
  predicate actually survived into the compiled SQL** — a query that loses its `law_firm_id` scope
  throws instead of silently running unscoped. See `src/modules/leads/leads.repository.ts` for the
  canonical example.
- `SqlRepository` is **deleted**. Simple CRUD extends `DrizzleRepository`
  (`../../shared/database/DrizzleRepository`), which takes the table object. ESLint blocks
  `extends SqlRepository` so the old shape cannot come back. A read that assembles its own SQL
  shapes its rows with `sqlRowToEntity` (`../../shared/database/rowShape`): camelCase, `Date` to
  ISO, and the generated `search` column dropped.
- Raw parameterized SQL directly on `pool` from `../../shared/database/db` is effectively gone —
  only reach for `parameterizedSql`/`tenantParameterizedQuery` (also in `queryContext`) when
  preserving a specific, planner-sensitive SQL shape, and only through an audited context.
- **Always** scope by `law_firm_id` via the query-context helpers — multi-tenant isolation is the
  app's job, not the DB's.
- Guard uuid params with `isUuid()` (`../../shared/utils/isUuid`) before querying uuid columns to
  avoid cast errors.
- Money is integer cents (`*_cents`). Junctions use replace-set semantics: delete-then-insert
  inside a transaction (`withDrizzleTransaction`, passing its executor to every nested call).

Validation rules:
- Use Zod
- Validate `body`, `params`, and `query` in one schema
- Use `z.coerce` for numeric query params
- Let the centralized validation middleware throw `ValidationError`

Event rules:
- Event constants live in `src/shared/events/eventTypes.ts`
- Naming format is `MODULE_ACTION`
- Event listeners in `*.events.ts` must be async and wrapped in try/catch

Time and formatting rules:
- Postgres returns native types. Drizzle gives `timestamptz` columns back as a JS `Date`, so
  convert to ISO when shaping output — repositories built on `queryContext`/`scopedWrite` do this
  manually per-row with `rowIso` from `../../shared/utils/dateConversion` (see `formatLead` in
  `leads.repository.ts`); `DrizzleRepository.toEntity()` and `sqlRowToEntity` do it
  automatically for the repositories and raw reads that use them. `date` columns (day-only) come back as raw `'YYYY-MM-DD'`
  strings via a type parser — do not wrap those in `new Date()`. There are no `Timestamp`
  objects and no `.toDate()`.
- Use `formatForClient` for timezone-aware display values
- Use `toTimestampOrNull` for storing parsed user date inputs

Performance and query guidance:
- Push filtering, ordering, and limits into SQL (`where`, `order by … nulls last`, `limit`/`offset`, `= any($1)` for id sets). Do NOT pull rows into memory to filter them.
- **Text search is `ILIKE '%term%'`, not full-text search.** Build the term with `toIlikeTerm()`
  (`../../shared/database/searchTerm`) and always pair it with `escape '\\'`. `court_catalog` is
  the one full-text user; `backend/AGENTS.md` has why the old `tsvector` columns were dropped.

Shared imports to prefer:
- Auth middleware from `../../shared/middleware/auth`
- Timezone middleware from `../../shared/middleware/timezone`
- Validation middleware from `../../shared/middleware/validate`
- Permissions from `../lawfirms/roles/requirePermission`
- Membership assertions from `../../shared/utils/membership`
- Time helpers from `../../shared/utils/time`
- Query helpers from `../../shared/database/queryContext` (`tenantQuery`, `firmQuery`,
  `withDrizzleTransaction`, …) and `../../shared/database/scopedWrite` (`scopedInsert`,
  `scopedUpdate`, `scopedDelete`, …)
- Drizzle table definitions from `../../shared/database/drizzle/schema`
- `isUuid` from `../../shared/utils/isUuid`
- Firebase bindings from `../../shared/database/firebase` — Auth and GCS only, never for data

Module style: **write new files in TypeScript with `import` throughout.** Many existing files
mix ES `import` (for Drizzle, the schema and the query contexts) with CommonJS `require()` (for
sibling modules, `.validation.ts` and most `shared/` utils). That mix is history, not a target:
about 350 source files still call `require()`. When editing an existing file, match what is
already there rather than converting it mid-change; when creating one, use `import`.
