# Calendar (with Google + Outlook two-way sync)

## Summary

Paralegix renders a calendar that aggregates tasks, matter events, client events, invoice/billing dates, and "external" events synced in from a user's connected Google or Microsoft (Outlook) calendar. Sync is **two-way and per-user**: outbound (Paralegix → provider) is driven by an in-process event bus when entities change; inbound (provider → Paralegix) is driven by provider push notifications (Google Watch channels / Microsoft Graph subscriptions, both registered in `calendar_subscriptions`) plus a throttled foreground poll. A shared adapter layer (`calendarAdapters.ts`) normalizes every entity type into "calendar items" so the engines stay entity-agnostic. The inbound upsert chain, cross-sync, loop guards, and delete reconciliation live once in a shared engine (`shared/providerSyncEngine.ts`) driven by two thin provider **strategy** objects (`google/googleStrategy.ts`, `outlook/outlookStrategy.ts`). Sync also **cross-syncs** the two providers: an inbound Google change is re-pushed to Outlook and vice-versa, with layered loop suppression to stop a ping-pong. Inbound webhook processing is **durable**: when async processing fails, the route persists a coalesced work item in `calendar_sync_failures` and a cron sweep retries it with exponential backoff (at-least-once delivery).

## Key Takeaways

- **One shared engine, two strategies.** The inbound priority chain, cross-sync, loop guards, the outbound-push stamp, and the cancelled/deleted reconciliation live in `shared/providerSyncEngine.ts` (`createEngine(strategy)`, `:152`). `google.service.ts` and `outlook.service.ts` build an engine from their strategy and delegate; each still owns its outbound body building, timezone handling, calendar resolution, and watch/subscription lifecycle.
- **Inbound webhook processing is durable.** Both webhook routes persist a pending `calendar_sync_failures` row for a verified notification BEFORE they acknowledge it, process it, and resolve the row only when processing succeeds. A notification the route cannot persist is answered `503` so the provider redelivers it. The cron `/api/cron/calendar-watch` renews channels and subscriptions, retries failed channel stops, replays failed outbound writes, then runs `retryFailedWebhooks()` (`calendarWebhookRetry.ts`), dead-lettering after 8 attempts. Backing table: `calendar_sync_failures` (`db/schema/60_calendar.sql`).
- **Outbound provider writes are durable too.** A push is recorded as an `outbound` work row first and dispatched under the sync lock (`calendarOutboundRetry.ts`, `dispatchOutboundWork`). A transient failure (a 429, a Google rate-limit 403, a 5xx) leaves the row for the cron to replay; `fetchCalendarRequest` (`calendarHelpers.ts`) also retries rate limits in place.
- **OAuth tokens and per-provider sync state live in `user_oauth_tokens`** (`db/schema/10_identity.sql:129`, one row per `(user_id, provider)`): tokens, the calendar id, the app calendar id, the sync cursor (Google `syncToken`) and the direction flags. The old `user_settings` table is gone. `calendarTokens.loadUserData()` (`calendarTokens.ts:27`) assembles the flat `userData` shape the engines consume.
- **Outbound sync is event-driven**, not request-driven. `calendar.events.ts` listens for `TASK_*`, `MATTER_EVENT_*`, `CLIENT_EVENT_*`, `INVOICE_*` and `MATTER_MEMBERS_UPDATED` (`:416-688`) and fans out to every relevant user × both providers, coalescing bursts for 1.5 s (`COALESCE_WINDOW_MS`, `:104`). Each (entity, user) sync runs under a `CALENDAR_SYNC` advisory lock that holds a pool connection across the provider calls, so one unit can hold up to 3 connections (that lock, an `OAUTH_REFRESH` lock during a token refresh, and a working query). A fan-out to matter members, task assignees or billing recipients, and a member backfill, therefore run 2 units at a time (`CALENDAR_SYNC_WIDTH`, `:53`: a 6-connection budget out of the 12-connection pool). `MATTER_MEMBER_SYNC_CONCURRENCY` still overrides the fan-out width.
- **Inbound sync** uses incremental deltas: Google `syncToken` (paged, capped at `MAX_DELTA_PAGES = 50`, `google.service.ts:1580`) and a fetch-by-id per Microsoft Graph notification (`processSubscriptionNotification`, `outlook.service.ts:1631`). A throttled full-list poll (`syncFromGoogle` / `syncFromOutlook`) backs this up when the page is open. `syncFromOutlook` throws when it hits its page cap or when any event fails to import (after importing the rest), so a `catch_up` retry stays queued instead of resolving over lost work. Outlook finds the dedicated Paralegix calendar by the stored id and creates a new one only when Microsoft reports it gone (404/410).
- **Echo suppression is by version, not by time.** Every push records the version the provider reported for this member's copy (`calendar_mappings.pushed_version`: the Google `etag`, the Outlook `changeKey`). An inbound event is skipped only when its version equals that one, so a genuine edit made seconds after a push is still imported. Last-writer-wins by `*LastModified`/`updatedAt` and a per-entity lock (`CALENDAR_ENTITY`) remain; a waiter that times out on that lock throws so the work is retried rather than dropped.
- **Copies go to the people an item is assigned to.** A matter or client event is pushed to its assignees (or its creator when it has none), and a task to its assignees and creator, not to the whole matter roster; clients are never invited. Each recipient must still be a firm member who can see the matter. `syncAssignedRecipients` (`calendar.events.ts`) deletes copies held by anyone who no longer qualifies, and `MEMBER_REMOVED`, `MEMBER_ROLE_CHANGED` and `ROLE_PERMISSIONS_CHANGED` re-run that reconciliation. An inbound edit to a shared item queues the same fan-out so colleagues' copies follow it.
- **Cancelled and completed items leave the calendar.** The adapters produce no calendar items for a cancelled event or a completed task, so the next push removes the provider entries.
- **Provider → entity resolution** on inbound goes through `calendar_mappings`; a delta page batches its mapping lookups into one query (`getMappingsByExternalIds`, `calendarSync.repository.ts:110`) and the prefetched cache is consulted first.
- **Sync routes are permission- and plan-gated.** `calendarSyncGates.ts` supplies `requireSyncPerm*` (the `calendar.sync` permission, checked first) and `requireCalendarSync*` (the `calendarSync` plan feature) for sync, event CRUD, batch sync and enable-silent-sync routes on both providers. The batch routes gate on the first item's firm, so `syncFirmGuard.ts` re-applies every gate per distinct firm before touching a row.
- **Synced-in external events are private to the member who owns them.** `calendarEventsRepo.listAll` and `findById` filter on `created_by = <user>`, and the inbound lookups by provider id are owner-scoped too, so two colleagues invited to the same Google meeting each get their own row. One member's personal Google/Outlook appointments never show up for colleagues.
- **Imported meetings keep their meeting details.** `calendar_events.provider_details` stores organizer, attendees and their RSVP, the join link, the provider's own link and privacy; `start_time_zone` stores the event's zone. A guest gets those details read-only (the API refuses an edit with `403`). An organizer's edit is refused with `409` until the caller confirms attendees will be notified; Google writes send `sendUpdates=none` unless that confirmation was given. A row imported before those details were recorded (`provider_details` is `{}`) is read from the provider first, with the importing member's connection, and the details are kept (`withMeetingDetails`, `calendarEvents.service.ts`); a provider that cannot answer refuses the change with `503`. An edit that moves only the start carries the end with it, and an end before the start is a `400`.

### Architecture: the shared engine + provider strategies

`shared/providerSyncEngine.ts` is the heart of the inbound + cross-sync logic. `createEngine(strategy)` (`:152`) closes over a single provider strategy and returns four delegated functions plus reused helpers:

| Engine export | Used by |
| --- | --- |
| `stampOutboundPush(userId)` (`:165`) | every successful outbound push stamps `last_outbound_push_at` on the user's `calendar_subscriptions` row |
| `crossSync(entity, entityType, userId)` (`:183`) | after an inbound write, re-push the entity to the SIBLING provider |
| `upsertExternalEvent(event, lawFirmId, userId, mappingCache)` (`:236`) | the inbound priority chain (below) |
| `processInboundDelete(eventId, lawFirmId, userId, mappingCache)` (`:359`) | shared by Google's `cancelled` delta branch and Outlook's `deleted` notification |

The **strategy** supplies only the provider-specific seams (see `googleStrategy.ts` / `outlookStrategy.ts`): field accessors (`getEventId`, `getEventModified`, `isCancelledEvent`, `getOriginatedBodyText`); field names (`lastSyncedField`, `lastModifiedField`, `otherLastModifiedField`, `externalIdPrefix`); resolution (`findTaskIdByEventId`, `findExternalByEventId`, `getExternalProviderId`/`getTaskProviderId`, `getSiblingAdapterEventId`); inbound builders (`buildTaskUpdateData`, `buildMappedEventUpdateData`, `buildExternalEventData`, `applyExternalLastModified`, `buildNewExternalEventData`); `syncBillingEvent`; and the watch-entity stamp target (`findWatchEntityForUser` / `stampWatchEntity`). The services lazily `require` each other via the strategy to break the require cycle.

### Data Flow (a): Create an entity locally and watch it reach the provider

Creating a *task* (the most common calendar item):

1. The tasks service emits `TASK_CREATED` on the in-process `eventBus` with `{ lawFirmId, taskId, entityData, userId, timeZone }` (`tasks.service.ts:219`).
2. `calendar.events.ts:397` handles it. With a `matterId` it fans out to all matter members; otherwise to the creator + assignees.
3. Per user, `syncToCalendars()` (`:203`) resolves cached `{ userData, settings }` (first running a cheap `getOutboundSyncCapabilities` pre-check, `:66`), skips users with no connected+enabled provider, then coalesces for `COALESCE_WINDOW_MS = 1500` (`:85`) so a burst collapses to one push (latest payload wins).
4. `performSyncToCalendars()` (`:140`) calls `googleService.createEventsFromEntity` (`google.service.ts:415`) then the Outlook equivalent (`outlook.service.ts:626`).
5. The adapter (`calendarAdapters.ts`) turns the task into calendar items. The service resolves any existing mapping first (so a re-dispatched event is a no-op, not a second entry), POSTs each new item, stamps the per-user `calendar_sync.google.<userId>.<key>.eventId`, saves a `calendar_mappings` row, and on success fires `stampOutboundPush(userId)`. Outlook mirrors this.

Reading: external events come straight from Postgres. `GET /calendar-events` → `listExternalCalendarEvents` (`calendarEvents.service.ts:54`) → `calendarEventsRepo.listAll` (`calendarEvents.repository.ts:189`), which returns only the caller's own rows (`created_by = <user>`), formatted with timezone-localized display strings. Tasks and matter/client events are read by their own modules (`GET /matters/events` and `GET /clients/events`, both bounded by a `from`/`to` range) and merged client-side in `Calendar.tsx`. The feed and task fallback read use `includeSpanning=true` to include all-day tasks starting before the window whose exclusive end overlaps it. Multi-day tasks render on each covered day but count once in the status totals. Timed form values retain an offset when needed to distinguish the repeated hour at DST fallback.

### Data Flow (b): The external sync loop

**Connecting (OAuth tokens):** Tokens are obtained during Firebase OAuth login and persisted to `user_oauth_tokens` via `calendarTokens.saveTokens` (`calendarTokens.ts:210`). The same row, one per provider, holds the per-provider sync state: `calendar_id`, `app_calendar_id`, `sync_cursor` (Google's `syncToken`) and the direction flags (`is_sync_from_provider`, ...); everything else lives on `users.preferences`. `loadUserData()` (`:27`) reads them back into the flat `googleAccessToken` / `microsoftAccessToken` / `googleSyncToken` / `outlookTimezone` shape.

**Enabling silent sync (push channels):** `enable-silent-sync` leaves the user with exactly one channel or subscription, so a reconnect or a double-click collapses to one. Google creates the new channel first and stops the old ones only once it is stored, then records a `catch_up` row; Outlook stops every existing subscription (`stopAllSubscriptions`) and then creates one.
- Google: `createWatchChannel` (`google.service.ts:1222`). Requires `WEBHOOK_BASE_URL` to be HTTPS. Registers an `events/watch` channel with a 7-day TTL (`:1245`) as a `calendar_subscriptions` row (`provider = 'google'`), then captures a baseline `nextSyncToken` via `initSyncToken`. Google returns that token only on the last page of a listing, so `initSyncToken` follows `nextPageToken` at 2,500 events a page (capped at 20 pages) until it arrives.
- Outlook: `createSubscription` (`outlook.service.ts:1442`). Creates a Graph subscription on `/me/events` as a `calendar_subscriptions` row (`provider = 'outlook'`). Graph first POSTs a `validationToken` the webhook echoes back (`outlook.webhook.routes.ts:33-35`).
- Outlook lifecycle: every subscription is created with a `lifecycleNotificationUrl` of `/api/webhooks/outlook-calendar/lifecycle`. That route echoes the `validationToken` handshake, verifies each item's `clientState` in constant time like the change route, and hands it to `handleSubscriptionLifecycleEvent` (`outlook.service.ts`). `reauthorizationRequired` renews the subscription (a PATCH of its expiry, which reauthorizes it, falling back to a recreate). `subscriptionRemoved` queues a `catch_up` row and then recreates the subscription. `missed` only queues a `catch_up` row, which the cron replays as a full `syncFromOutlook`. Graph cannot add a lifecycle url with a PATCH, so renewal reads the subscription Graph returns from its PATCH and recreates any that lack the current url (one created before the route existed, or under another webhook base). The PATCH has already extended it, so a refused recreate leaves it live and the next renewal tries again. A lifecycle item delivered to the change route instead is verified the same way and handed to the same handler, never queued as a change.
- Renewal: cron `/api/cron/calendar-watch` → `renewExpiringChannels` (`google.service.ts`) and `renewExpiringSubscriptions` (`outlook.service.ts`). Both create the replacement before retiring the old one (Outlook through `replaceSubscription`, on the stale-resource path and when a PATCH fails), so a failed create leaves the old channel or subscription recorded and still delivering. A channel stop that fails is queued as a `calendar_sync_failures` row of kind `stop_channel` (`recordWatchChannelStopFailure`, `calendarSync.repository.ts:536`) and retried by `retryUnstoppedWatchChannels` (`app.ts:659`). Every replacement of one user's watch (Google renewal and `rearmWatchChannel`; Outlook renewal, `rearmSubscription` and the lifecycle handler) runs under the `CALENDAR_WATCH` lease keyed `provider:userId`, and re-reads the row it is replacing once it holds the lease. Two overlapping replacements each used to create a new watch and stop the old one, leaving two live and every change notifying twice. Renewal takes the lease with `tryLock` and leaves a user whose watch is already being replaced to the next run; the re-point and the lifecycle handler wait for it. A Google notification for a channel that has no `calendar_subscriptions` row but does have a `stop_channel` row, and whose `X-Goog-Resource-ID` matches that row, is stopped then and there (`stopLingeringChannel`) and never synced, which reaches channels whose stop retries are spent.

**Inbound notification → reconcile (Google):**
1. Google POSTs headers only to `/api/webhooks/google-calendar`.
2. `google.webhook.routes.ts` acknowledges `sync` handshakes, looks up the channel and verifies the token. It then persists a pending work row for the member, and answers `503` if it cannot, so Google redelivers. There is no calendar-wide "recent push" skip: our own echoes are recognised per item inside the inbound chain.
3. It calls `processWatchNotification`, resolves the pending row under its lease on success, and only then answers `200`. A processing failure leaves the row for the cron, marked `changeType = 'deleted'` with the event id when the failure was a cancelled event.
4. `processWatchNotification` (`google.service.ts`) takes a per-user advisory lock and runs the delta: paged with `showDeleted=true` and capped at `MAX_DELTA_PAGES`. Hitting the cap is not a silent stop: the next page token is kept in `meta.googleDeltaPageToken` and the work stays pending, so the next run resumes where this one stopped. On `410 Gone` it re-baselines and runs a full sync; the new baseline token is committed only after that full sync succeeds. The advanced `nextSyncToken` is saved only after every changed event has been written. It dedupes changed events by id, prefetches every event's mapping row in one query (`getMappingsByExternalIds`, `:1678`), then per event calls the engine: `processInboundDelete` for anything `googleStrategy.isGoneForUser` reports (cancelled, declined, a working-location marker or birthday), plus the occurrences of a gone series (ids `<parent>_<start>`); `syncGoogleSeries` for a series parent (below); otherwise the upsert path. The first per-event failure is re-thrown after the loop (`:1685`, `:1701`) so the route can queue a retry. Transient delta failures (429, 5xx, rate-limit reasons) throw; terminal auth failures return (`:1606-1626`).
5. `engine.upsertExternalEvent` (`providerSyncEngine.ts:236`) resolves the target in priority order: existing **task** (by provider id) → existing **external event** (`calendar_events`) → existing **mapping** (task / matterEvent / clientEvent / billing; every task the real-time sync pushes is found here, because its event id lives in the per-user map rather than the scalar column step one reads), applied under the `CALENDAR_ENTITY` advisory lock with the mapping's own firm (`:317`) → Paralegix-originated-marker skip (`:333`) → else create a new `calendar_events` row. Each branch applies the loop guards and, on success, cross-syncs to the sibling provider.

**Inbound notification → reconcile (Outlook):**
1. Graph POSTs JSON `{ value: [...] }` to `/api/webhooks/outlook-calendar`. The route dedupes notifications per `(subscriptionId, eventId, changeType)` and caches tokens per batch. There is no calendar-wide "recent push" skip for `updated`.
2. For each notification it persists a pending work row, processes it, and resolves the row on success; a failure leaves the row for the cron. The route answers `202` once the batch is stored and processed, and `503` if it could not store it, so Graph redelivers. Processing the batch before the `202` is bounded by Graph's response deadline; a slow batch is the cost of never acknowledging work that was not saved.
3. `processSubscriptionNotification` (`outlook.service.ts:1631`) handles `deleted` via `engine.processInboundDelete` (`:1651`); for `created`/`updated` it fetches the full event by id from Graph, treats 404/410 as gone, throws a `retryable` error on 429/5xx (`:1669-1685`), then upserts via the same priority chain.

### Data Flow (c): The durable webhook-retry path

1. **Record before processing, keep on failure.** The webhook routes write the row before they process the notification and delete it once processing succeeds, so a crash between the two leaves work to retry rather than nothing. `recordWebhookFailure({ provider, userId, lawFirmId, changeType?, eventId?, resource?, error })` (`calendarSync.repository.ts`) upserts a `calendar_sync_failures` row of kind `webhook` with `dedupe_key = '<provider>:<userId>'`, so repeated failures for one user coalesce onto one row. Each failure bumps `attempts` and sets `next_attempt_at = now() + min(2 h, 30 s · 2^(attempts+1))` (policy `:32`, SQL `:397-409`); a row that had already exhausted its budget is reset to `attempts = 1`, due now.
2. **Sweep on cron.** `/api/cron/calendar-watch` runs `retryFailedWebhooks` (`calendarWebhookRetry.ts:77`) after the renewals. It lists due rows (`listDueWebhookFailures`, `calendarSync.repository.ts:507`: `next_attempt_at <= now()`, budget not spent, not expired).
3. **Retry = replay then resume.** `retryOne` (`calendarWebhookRetry.ts`): for Google, a recorded delete is first replayed through the idempotent `processInboundDelete` (`reprocessInboundDelete`), then `processWatchNotification` runs the delta again from the last COMMITTED cursor, which never advanced past the failed events. For Outlook it re-invokes `processSubscriptionNotification` with the stored `changeType`/`eventId`. A `catch_up` row (recorded on reconnect and on a calendar switch) runs a full sync instead: `forceFull` for Google, `syncFromOutlook` for Outlook.
4. **Resolve or reschedule.** Success deletes the row (`:94`); a repeat failure reschedules it (`:101`). Once `attempts` reaches `WEBHOOK_RETRY_MAX_ATTEMPTS = 8` the row stops being selected, and each sweep logs a count and a sample of dead-lettered rows (`:107-118`).

Idempotency is the correctness anchor: the inbound upsert chain dedups by provider event id and resolves conflicts last-writer-wins, so a duplicate retry cannot create duplicate events.

Outbound work is stored separately with kind `outbound`. External-event edits and deletions queue every linked provider before attempting either write. A failed ownership lookup keeps deletion work pending, and a successful retried external deletion clears its provider ids before removing the local row. Shared-item writes read current assignments at dispatch, so queued work cannot recreate a removed assignee's copy. Inbound fanout must persist every recipient's work before the cursor advances; replay queues the saved state if the original write committed before its fanout failed. External sibling writes and deletions use the same queue. A sibling provider failure leaves durable work, and a queue failure preserves the original notification and source row for replay.

The **`calendar_sync` jsonb map** (on tasks, events and invoices) is shaped `{ google: { <userId>: { <itemKey>: { eventId } } }, outlook: { <userId>: { <itemKey>: { eventId, changeKey } } } }`, mutated in `applyCalendarSyncDescriptor` (`calendarSync.repository.ts:584`). ### Key Logic & Rules

**What "connected" means.** One module, `shared/calendarGrant.ts`, decides it for every reader: the check-auth routes, `GET /api/settings/user` (`googleCalendarState`, `microsoftCalendarState`, and the derived `loggedInWithGoogle` / `loggedInWithMicrosoft`), General Settings and the outbound-sync pre-check (`getOutboundSyncCapabilities`, which needs a refresh token and no recorded grant problem). A row is `disconnected` without a refresh token, `reconnect_required` after a refresh was refused with `invalid_grant`, `permission_required` when its recorded scope lacks the calendar permission, `unverified` when it predates scope recording (check-auth resolves it once through a `POST` to Google `tokeninfo` with the access token in the form body, or one Microsoft refresh), and otherwise `connected`. Background and webhook sync obey the same rule: `loadUserData` (`calendarTokens.ts`) withholds a provider's tokens unless the state allows sync, so webhooks, watch renewal and manual sync make no provider call for a dead or downgraded grant, and manual sync and the calendar list answer with the reconnect error instead. Stopping a channel or subscription reads the tokens ungated. The frontend raises the existing reconnect banner when the settings read reports `reconnect_required` or `permission_required`. The browser can no longer write these keys (nor `googleCalendarState` / `microsoftCalendarState`): the settings write rejects `loggedInWithGoogle`, `loggedInWithMicrosoft` and `googleConnectedEmail`. How a connection is made is in [Authentication](/features/authentication).

**Token storage & refresh.** Tokens are read once per fan-out and cached briefly. API calls auto-refresh on `401`. Concurrent refreshes for the same `(provider, user)` collapse into one in-flight promise per process (`dedupeRefresh`, `calendarHelpers.ts:15`), and a DB lock serializes refreshes across instances (`calendarHelpers.ts:25-60`), which matters for Microsoft because its refresh tokens rotate. On no or failed refresh, `requiresReAuth: true` propagates and the frontend surfaces a reconnect banner. A refresh writes with one update keyed on the user, provider and the refresh token it redeemed, so a refresh that started before a disconnect or a reconnect can neither recreate the deleted row nor overwrite the newer connection. Every refresh records what it learns: the refreshed `scope`, `meta.grantState` (`reconnect_required` for `invalid_grant`, `permission_required` for a scope without calendar access, cleared when access returns; a 5xx records nothing), and, for a row connected before identity was recorded, the account its ID token names. A Google 403 for insufficient scope records `permission_required` without a pointless refresh.

**Dedup of sync echoes.**
1. **No calendar-wide window.** The webhooks used to skip every notification for 90 s after any push to that calendar, which held back real edits to unrelated events (and lost them on Outlook). `last_outbound_push_at` is still stamped but no longer read by the webhooks.
2. **Version match:** an inbound event whose `etag` / `changeKey` equals the mapping's `pushed_version` is our own write coming back and is skipped. Anything else is a real change, however soon after a push it arrives. (This replaced a 180 s time window that dropped genuine edits made inside it.)
3. **Last-writer-wins:** for an item a mapping links, `mappedInboundIsStale` takes the provider edit when it was made after that copy's last push (`calendar_mappings.pushed_modified_at`), unless the sibling provider's `*LastModified` is newer or a Paralegix edit not yet pushed anywhere (`updatedAt` after every `lastSyncedTo*`) is newer. `updatedAt` alone could not decide, because every push stamps it. A mapping with no recorded push, and an imported row, keep `siblingOrParalegixIsNewer` (the sibling `*LastModified` and `updatedAt`). A description marker (`isParalegixOriginated`) catches Paralegix-originated events whose mapping row is missing.
4. **Write access:** a mapped edit is written only when the member could make it in Paralegix (`tasks.update` and the matter seat for a task, `matters.update` and `assertEventWriteAccess` for a matter event, `clients.manage` for a client event). Otherwise the item's state is pushed back over that member's copy.
5. **What an edit carries:** Google leaves an empty field out of the event, so a whole event without a description or location means it was cleared. A provider location lands in `location`, the column the push reads first; a client event's court name coming back is not copied onto the event. A shared event keeps its zone unless the copy's start or end moved to a zone with a different clock; a zone-less event takes only a zone other than UTC or the member's own, which a push fills in. A description whose Paralegix footer the member deleted is stripped by the entity type the mapping names.
6. **Entity lock:** mapped-entity updates run under `advisoryLock.withLock('CALENDAR_ENTITY', ...)` and re-read state inside the lock; a waiter that times out throws, so the notification stays pending and is retried rather than lost.

**"Sync existing" buttons.** The settings page's bulk pushes (`syncTasksTo*` / `syncEventsTo*`) create each event through the same per-item path as the real-time sync (`createGoogleEventIfMissing` / `createOutlookEventIfMissing`) and under the same `CALENDAR_SYNC` lock (`shared/calendarSyncLock.ts`). They record the event in the pushing user's `calendar_sync` entry plus a `calendar_mappings` row, never the scalar `google_event_id` / `outlook_id` column, so a later time change PATCHes that event instead of creating a second one. The event is built from the saved row alone, exactly as the per-change sync builds it (the request only names which rows to push), so a bulk copy and the next edit's PATCH carry the same title, description, location and zone. Who gets a copy is `isCalendarRecipient` (`shared/calendarRecipients.ts`), the rule the per-change retry also applies: a task goes to its creator and assignees, an event to its assignees or, with none, its creator. The matter-member backfill in `calendar.events.ts` applies the same rule. A row with no recorded creator counts the member who saved it as creator only on the per-change path and its retry; a bulk press or a backfill pushes it to nobody, since the next save would delete that copy. The matter wall is asked of the matter the request names and of the row's own matter (`matterWallFor`, `syncFirmGuard.ts`), since the settings screen sends no matter for a task. `isExistingItemEligible` (`calendarTime.ts`) then skips anything cancelled, completed or already past, judged on the saved row so a stale request cannot resurrect it. The events button sends matter events and client events together (`buildExistingEventsPayload`, `frontend/src/lib/utils/existingEventsSyncPayload.ts`): an item names a matter event by `matterId` or a client event by `clientId`, and `loadBatchEvent` (`calendarEntityResolver.ts`) reads the row under the item's firm and picks the adapter.

**Inbound changes to a mapped item.** A matter or client event moved in the provider takes its new end as well as its new start (`inboundEndsAt`, `providerSyncEngine.ts`): the provider's end for a timed event, the old end shifted by the same amount for an all-day one. An event with no end of its own takes the provider's end only when it is not the one-hour block the push filled in. Without it the `events_ends_after_start` CHECK rejected any move past the old end. The member's own provider id and change key are never written into the event's shared scalar columns. An Outlook meeting its organizer cancelled (or one the member declined but kept) arrives as `updated` and is handled as a delete.

Ordinary matter and client event edits preserve the original event zone when the submitted start instant and all-day flag are unchanged. Moving or postponing the event records the zone in which the new date was entered. Selecting a matter's court for an existing event in the client tab does not fill an empty venue with that court. Editing an imported source meeting updates it without creating an ownership mapping; disconnect cleanup only removes copies Paralegix created.

**Description round trips.** `stripCalendarHeader` / `stripSourceMarker` (`shared/calendarHelpers.ts`) remove the generated header, app link and source marker before inbound Google or Outlook descriptions become notes. Source markers must occupy their own lines, so ordinary sentences mentioning a task or event from Paralegix are preserved and do not suppress a third-party import. Origin detection converts HTML to text before checking the same marker pattern. Parenthesized source markers are removed as a whole even when their parentheses are on separate lines. The calendar side panel suppresses a stored note or task description consisting only of empty parentheses, including older sync artifacts, while preserving parentheses within real text. Imported-event edits (`calendarEvents.service.ts`, `updateExternalCalendarEvent`) treat explicit null notes or location as a clear; omitted fields retain their saved values. Clearing notes also clears the synced description. Outbound updates send an explicit empty location to both providers so a cleared venue disappears there too. A task is the exception: inbound sync never reads a task's location back, so a location the member added in the provider is theirs, and an update sends an empty one only when that save cleared a location Paralegix had set (`locationCleared` on the `TASK_UPDATED` payload, read by the task adapter as `keepProviderLocation`). The flag describes one save, so when a later save replaces the queued outbound payload before it runs, `recordOutboundWork` carries the set flag into the replacement (`OUTBOUND_ONE_SHOT_FLAGS`, `calendarSync.repository.ts`). External description builders use the saved description when notes are whitespace-only.

**Removing a shared item from one calendar.** Removing a task, matter or client event, or billing date from a member's provider calendar unlinks that member's copies (this provider's per-user entry and mapping, and their copy on the sibling provider). It never cancels or deletes the item for the firm; cancelling happens in Paralegix.

**Repeating events.** A notification reports a series by its parent. `syncGoogleSeries` / `syncOutlookSeries` list the occurrences from 30 days back to a year ahead instead, import each, and remove a parent imported as one event before this existed (`removeImportedSeriesParent`). A parent that is a copy Paralegix pushed, because the member made a Paralegix item repeat, stays linked to its item. Occurrences carry their series in `series_event_id` (migration 0016); Google occurrence ids are also `<parent>_<start>`, so rows imported before the column existed are found too. A deleted or edited series therefore removes its stale occurrences at once on both providers. Occurrences are not copied to the sibling provider (`isRecurringInstance`), since they would land there as dozens of one-off events.

**One meeting on both calendars.** Imported rows carry the invitation's iCalendar UID (`ical_uid`, migration 0016), normalized by `normalizeICalUid` (`calendarHelpers.ts`): Graph reports `iCalUId` as the hex of the meeting's Global Object Id, which for a meeting organized outside Exchange wraps the original UID behind a `vCal-Uid` tag. When a new event matches a row this member imported from the other provider, the engine links it to that row instead of importing it again, and deletes the copy Paralegix had pushed to this calendar earlier (the link is written first, so that copy's delete notification cannot take the row with it). A row whose two provider ids are both the member's own invitations (neither has a `calendar_mappings` row, which every Paralegix copy gets) is never pushed across, and removing one side keeps the row on the other. Occurrences of a repeating event are not matched, since Google gives every occurrence the series' UID. If a copy is being pushed at the moment the matching invitation arrives, the row can briefly point at the copy; the next change or full poll relinks it and removes the copy.

**Deletions the poll catches.** After a complete full listing of the main calendar, `engine.removeUnlisted` runs the delete path for every event this member imported from that provider that starts inside the window (one day in from each edge) and was not listed. It is skipped when the listing was truncated, and when the Paralegix calendar is targeted (a different calendar from the one events were imported from). The same pass reconciles this member's copies of Paralegix items (`calendar_mappings`): a copy whose item starts in the window, is not listed, and that the provider confirms is gone (404, 410 or cancelled on a direct read) is unlinked through the delete path. That covers a deletion whose notification was lost behind a `410`. Before it, a later edit found the id gone and recreated the copy.

**Switching the calendar target** re-points live import (`rearmWatchChannel` / `rearmSubscription`, called from `settings.service.ts`): the Google sync token is cleared, and an existing channel or subscription is recreated on the new calendar. A member without one is not given one. A Google channel that still watches a calendar other than the current target (one created before the target changed) is re-pointed the same way by its next notification, which then runs a full sync of the target calendar. A notification that finds no stored token takes one before running its full sync. Outlook does the same for a subscription whose resource names a calendar other than the target (`repointStaleSubscription`, called from the webhook route once per subscription per batch): it is recreated on the target, the target calendar is read in full, and the notifications from the old calendar are dropped. Renewal recreates such a subscription instead of PATCHing it, because a PATCH keeps the resource. A switch also queues a relocation for every mapped Paralegix copy, so existing copies move to the newly selected calendar, and records a `catch_up` work row so the new target is read in full. Neither provider rewrites the time zone of a whole calendar or mailbox any more; each pushed event carries its own zone. Google finds the dedicated Paralegix calendar by the stored calendar id rather than by name.

**Disconnecting a provider** (`forgetProviderConnection` in `auth.service.ts`, which also runs when a reconnect picks a different account) revokes a Google grant at `oauth2.googleapis.com/revoke` on a best-effort basis (Microsoft has no per-app revoke for delegated tokens, so the row is only deleted), stops the watch channel or subscription, and through `calendarEventsRepo.forgetProviderImports` deletes what the member imported from it, except events also copied to their other calendar while that one is still connected, which become owned by it. Provider ids and per-user map entries are kept, so a reconnect updates the same events instead of copying them again. The disconnect routes take an optional `removeParalegixEvents: true` (offered in General Settings): `removeProviderCopies` first deletes the copies Paralegix pushed to that provider. A reconnect records a `catch_up` work row so changes made while disconnected are imported.

**Where time handling lives.** Nothing in the calendar module formats, parses or anchors a date by hand. The instant and wall-clock conversions are in `shared/utils/time.ts`: `zonedWallClock` (an instant as a zone's wall clock, the form Graph takes), `zonedWallClockWithOffset` (the same with the zone's offset, the form Google is sent, so the repeated hour when clocks go back names one instant; Graph has no offset field, so Outlook keeps that ambiguity), `wallClockToUtc` (back again), `dayAnchor` (a day-only value at noon UTC) and `toInstant` (any stored value as an instant, a bare day taking its anchor rather than midnight UTC). The push arithmetic both providers share is in `shared/calendarTime.ts`: the one-hour `DEFAULT_TIMED_BLOCK_MS`, `timedEnd`, the exclusive-end `allDaySpan`, the full-poll and series read windows and `startDayIn` (the local day a timed provider start falls on, which an invoice date takes). Outlook's Windows zone names and Graph date parsing are in `outlook/outlookTime.ts`. When a task is due is `taskDueInstant` (`tasks/taskDue.ts`): its `dueAt` when it has a time, else its day's anchor. The task responses, the engine's task state and the push all read it, so they cannot disagree.

**Ends.** Matter events, client events and tasks share one set of rules for an optional end, in `shared/validation/eventRange.ts`. A timed end is an instant; an all-day end is the exclusive day after the last day, at noon UTC, the shape Google and Outlook take, so the forms show the last day and add one on save. `assertEndAfterStart` turns the database's after-start CHECK into a 400. When an edit moves the start without sending an end, `endWithoutCallerEnd` carries the end along so the item keeps its length, and drops it when the all-day flag flips. Postpone and recurrence follow the same rule. Inbound sync (`inboundEndsAt` in `providerSyncEngine.ts`) takes a timed provider event's own end, and an all-day one's own exclusive end day (each strategy's `getAllDayEnd`), so a span lengthened in Google or Outlook, or an item switched between timed and all-day there, comes back with the end the provider shows. Null removes an end. The forms keep the end's day when All day is toggled (`endAcrossAllDayToggle` in the frontend's `calendarTiming.ts`). Responses return `endsAtLocalDisplay` and `endsAtLocalInput` beside the start's, from `endsAtLocal`.

**All-day to timed on Google.** Google merges a PATCHed `start`/`end` into the stored one, so `updateEventsFromEntity` sends the replaced form as an explicit null (`replacingEventRange`); otherwise giving an all-day item a time leaves both `date` and `dateTime` set.

**Tenancy.** Every read/write is scoped by `law_firm_id`; the external-events routes assert `assertLawFirmMembership`, and external events are further limited to their owner (`created_by`). Subscriptions and mappings carry `law_firm_id`, and a mapped entity is written under the mapping's own firm, not the webhook's, so a user in two firms does not lose inbound changes. Batch sync routes re-check permission, plan and billing per distinct firm in `syncFirmGuard.ts`.

**Timezone / date handling.** Google uses IANA zones directly; Outlook returns and accepts **Windows** zone names, so `outlook.service.ts` keeps a `WINDOWS_TO_IANA` map (`:33`) and converts both ways. Dates are formatted to a zone-local wall-clock string without an offset (Graph requirement). All-day events use UTC date arithmetic to dodge off-by-one.

### Dependencies

- **Google Calendar API v3**: `calendarList`, `calendars`, `events`, `events/watch`, `channels/stop`. Refresh via `https://oauth2.googleapis.com/token`.
- **Microsoft Graph v1.0**: `/me/events`, `/me/calendars`, `/me/calendarView`, `/me/mailboxSettings`, `/subscriptions`. Refresh via `https://login.microsoftonline.com/common/oauth2/v2.0/token`.
- **Env vars:** `WEBHOOK_BASE_URL` (HTTPS or silent sync is disabled), `GOOGLE_CLIENT_ID/SECRET`, `MICROSOFT_CLIENT_ID/SECRET`, `DATABASE_URL`, cron auth (`authorizeCronRequest`).
- **Internal:** `eventBus`, the adapter registry, `providerSyncEngine` + the two strategies, `calendarSync.repository`, `calendarWebhookRetry`, `calendarSyncGates`, `syncFirmGuard`, `shared/database/advisoryLock`, the per-entity repos, `invoicesService`.

### Dispatch-time connection checks

Google and Outlook outbound create/update/delete functions read current connection data when they run. A token snapshot passed by the debounce queue cannot keep a disconnected connection active. Calendar window failures expose retry through the existing query hooks. The event-listener suite covers disconnecting each provider while its create is queued.

## What Can Be Improved

Priority order, highest impact first. Resolved and dropped (verified): the duplicated inbound paths (shared engine + strategies); unbounded delta and full-sync loops (`MAX_DELTA_PAGES`, `MAX_SYNC_PAGES`); un-batched mapping lookups; fire-and-forget webhooks with no retry; silent drops of transient Google and Outlook fetch failures; the pre-increment backoff exponent; dead-lettered rows swallowing new failures (now reset); inbound writeback under the webhook's firm instead of the mapping's; the orphaned-delete retry gap (now replayed first); duplicate channels on reconnect; cross-instance Microsoft token-refresh races (now a DB lock); one member's synced-in external events being visible to the whole firm (now filtered by `created_by`); time-based echo suppression (now `pushed_version`); acknowledging a webhook before its work was stored; and committing a Google cursor before its events were written.

### 1. Foreground poll ignores the incremental `syncToken`
`syncFromGoogle` (`google.service.ts:759`) and `syncFromOutlook` (`outlook.service.ts:967`) page, but always list the full ±1-year window (`google.service.ts:771-785`) and re-upsert every event even when a sync token or live subscription exists. This spends Google/Graph quota on each foreground poll and on every Google webhook retry. Reuse the delta path when a token exists and fall back to the full list only without one.

### 2. Per-process in-memory state is unsafe across instances (Cloud Run scales horizontally)
The engine's `userIdToWatchEntityId` map (`providerSyncEngine.ts:163`), the coalesce map in `calendar.events.ts` (`:85`), and the Google timezone cache (`google.service.ts:100-105`) are process-local. On more than one instance the 1.5 s coalesce window does not dedupe across pods, but it no longer decides correctness: every outbound push for one (entity, user) already runs under the cross-instance `CALENDAR_SYNC` lock (`calendar.events.ts`, `withLock`), and token refresh runs under `OAUTH_REFRESH`. Both are lease rows in `lock_leases` (`shared/database/advisoryLock.ts`) that hold no pool connection while the provider calls run. What remains is wasted work: two pods can each push the same change in turn, the second as a PATCH rather than a duplicate create. A DB-backed coalesce would remove that.

### 3. Dead-lettered webhook rows are never removed
Webhook rows have a null `expires_at`, and the purge only removes expired rows (`calendarSync.repository.ts:422-433`), so a row that exhausted its 8 attempts stays in `calendar_sync_failures` forever and is only logged by each sweep (`calendarWebhookRetry.ts:107-118`) until a brand-new failure resets it. Add an auto-drain (delete after N sweeps or a TTL) or a real metric/alert sink.

### 4. Outbound code is still duplicated between the two services
The outbound halves remain near-identical: `createEventsFromEntity` / `updateEventsFromEntity` / `deleteEventsFromEntity` (`google.service.ts:415-605`, `outlook.service.ts:626-823`), the batch `syncTasksTo*` / `syncEventsTo*` (`google.service.ts:990,1100`; `outlook.service.ts:1176,1294`), and the route-level event CRUD differ only in API verbs, body shape and timezone handling. A second strategy seam for outbound bodies would let the loops live once.

### 5. Inbound upsert does sequential per-event lookups
The mapping lookup is batched, but per event the engine still issues sequential queries for the task (`findTaskIdByEventId`, `providerSyncEngine.ts:260`) and external-event (`findExternalByEventId`, `:277`) branches when the cache misses. Batch those the same way (one `= any($1)` query per table for the delta's id set).

### 6. The Outlook route does not thread a mapping cache
`processSubscriptionNotification` accepts a `mappingCache` (`outlook.service.ts:1631`), but the webhook route does not pass one (`outlook.webhook.routes.ts:108-115`), so each Outlook notification looks up its own mapping. Minor while Outlook notifications are processed one at a time.
